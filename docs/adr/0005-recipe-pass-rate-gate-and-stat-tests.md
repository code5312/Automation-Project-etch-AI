## 배경

팀원이 `식각_평가지표_정리_(11.13).pdf`를 전달했다. 400개 레시피 정답 데이터 전체를 실측해
평가 지표·합격 기준·승격 조건을 다시 도출한 문서이고, 문서 자체가 "저장소 수정은 저장소
관리 담당이 진행한다"고 명시해 반영 여부·범위를 이 저장소 쪽에서 판단해야 한다.

현재 코드(ADR-0004 기준)와 대조한 결과, 문서가 지적한 지표 재정의(§8 표)뿐 아니라
**게이트 판정의 집계 축 자체**(레시피 묶음 평균 vs 레시피별 개별 판정)도 다르다는 걸
확인했다 — 문서 §8 표에는 이 차이가 명시돼 있지 않지만, 실제 코드(`gate.py::
check_dimension_error`가 레시피 전체를 모아 평균 오차로 판정)와 문서 §3(레시피마다 판정 후
충족 비율로 합격)을 직접 비교해서 발견했다[확인, 2026-11-13].

## 결정 1: 신규 지표 추가 — 표면 Dice, HD95, 거리 지표의 y≤0 제한

`eval/metrics.py`에 없는 두 지표를 추가한다:
- `surface_dice(pred, true, tau=0.3)`: 0.05µm 간격으로 보충한 점 중 상대 곡선 τ 이내 비율
  (양방향 합산). `_densify_curve`/`_distance_to_curve` 재사용[문서 §7 그대로].
- `hd95(pred, true)`: 양방향 거리 각각의 95번째 백분위 중 큰 값.

거리 지표(표면 Dice·Chamfer·HD95)는 실리콘 부분(y≤0)만 계산하도록 제한한다 — 문서 실측:
마스크 포함 표면 Dice 0.59 vs 제외 0.01(마스크가 윤곽선 길이의 58%라 마스크 자체의 거의
무변화가 지표를 왜곡)[확인, 문서 §5].

## 결정 2: 기존 지표 재정의 (IoU·CD 측정 높이·테이퍼 분모·보잉)

| 지표 | 현재 | 신규 | 근거 |
|---|---|---|---|
| IoU | 전체 vacuum 영역(공기 포함) | 처음 고체였던 칸만 | 공기 영역은 항상 일치해 IoU가 부풀려짐 |
| CD 측정 높이 | y=0, 45%, 90% | 10%, 50%, 90% | y=0 폭은 마스크 구멍 폭에 가까워 측정 의미가 약함 |
| 테이퍼 분모 | `depth` | `0.8 × depth` | 측정 높이(10~90%, 깊이의 80% 구간)와 분모를 일치 |
| 보잉 | `중간CD − (위+바닥)/2` | `5~95% 구간 최대폭 − 5%높이 폭` | 최대 폭 위치가 항상 중간은 아님 |

`cd_profile`/`taper_angle_deg`/`bowing` 함수 시그니처·내부 계산을 문서 기준으로 바꾼다.
순수 함수 변경이라 영향 범위가 좁다[확인, 2026-11-13 코드 대조].

## 결정 2-1: 추론 속도 비 신규 추가 (보고용, 차단 없음)

`추론 속도 = ViennaPS 레시피당 시간(val 40 평균 940초) ÷ 모델 시간`, 측정 장비 병기.
현재 `measure_latency()`는 모델 지연시간만 단독으로 재고, ViennaPS 대비 비율은 전혀
계산하지 않는다 — `project-definition.md` §6도 "속도 이득은 미측정 [미확인]"이라고
명시해 둔 바로 그 항목이다. 합격선 없이 보고만 한다[문서 §2.3].

## 결정 3: 게이트 판정 집계 축을 "레시피별 통과 + 통과율 90%"로 변경

**기존**(`gate.py::check_dimension_error`): 레시피 묶음 전체를 모아 평균 오차 하나로 판정.

**신규**: 레시피마다 깊이·중간CD·롤아웃 3조건을 독립적으로 판정(각각 "마지막 스텝 오차 ≤
max(5%, 0.3µm)", "≤ max(5%, 0.6µm)", "오차 증가율 ≤2.5 또는 증가량 ≤0.3µm")하고, 세 조건을
모두 충족한 레시피 비율이 90% 이상(검증 40개 기준 36/40 이상)이면 합격.

근거: 이항분포 단측 95% 신뢰하한(Clopper-Pearson) — 36/40 충족 시 실제 충족률 하한 0.79,
40/40이어도 0.93. 36개 기준을 쓰면 "새 조건에서 약 80% 이상이 기준 안에 든다"고 95%
신뢰로 말할 수 있다는 것이 근거[문서 §5].

평균 집계의 약점(일부 레시피가 심하게 틀려도 나머지에 묻혀 통과 가능)을 레시피별 판정이
구조적으로 막는다는 점이 이 ADR의 채택 이유다.

`rollout_max_ratio`도 2.0 → **2.5**로 변경 — val 40 실측 오차 증가 패턴(일정 1.0 / 선형
2.5~2.9 / 제곱 5.5~6.9) 중 선형 증가의 최솟값이 2.5라, 기존 2.0은 정상적인 선형 증가
모델을 오탐 차단할 수 있다[문서 §5 "데이터 확인"].

**집계 축도 함께 바뀐다 — 이는 ADR-0004 결정3을 되돌리는 것**: ADR-0004는 "레시피
여러 개의 Chamfer를 **스텝 인덱스 기준으로 먼저 평균**한 시퀀스"를 반/반으로 나눠
비율을 봤다. 이 ADR은 **레시피별로** 오차 증가율(또는 증가량)을 따로 계산해 결정3의
3조건 중 하나로 판정한다. 이유: 레시피마다 깊이 도달 스텝 수가 달라(조기 종료 포함
20개, 20분까지 남는 레시피 21개) 스텝 인덱스 기준 평균을 쓰면 "전반 절반"과 "후반
절반"을 구성하는 레시피 집합 자체가 달라져 버린다[문서 §8 "이유" 란 그대로, 확인
필요한 기존 로직의 실질적 약점].

**계산 실패 레시피 처리**: 어떤 스텝이든 계산에 실패한 레시피는 깊이·CD·롤아웃 **세
조건 모두 미충족**으로 세고, 그 레시피의 IoU·표면 Dice는 0으로 처리한다 — 통과율
분모에는 포함하되 통과로 잘못 집계되지 않게 한다[문서 §3].

## 결정 4: 승격 관문 C(퇴보 없음)에 통계 검정 추가 — 관문 B(개선)는 범위 제외 [사용자 결정 2026-11-13]

**기존**(ADR-0004 결정2): ③(직전 챔피언 대비 평균 오차 악화 ≤10%)은 참고 지표일 뿐, 승격을
막지 않는다 — 즉 "직전보다 나빠도" 통과 가능.

**신규**(드리프트 트리거 경로, A+C만 — 아래 재결정 참고): 승격에 관문 C(퇴보 없음)를
추가한다.
- ① IoU가 챔피언 대비 유의하게 낮아지지 않음 — 윌콕슨 부호순위 검정(레시피별 1:1 비교),
  반대 방향 p ≥ α.
- ② 최악 레시피 HD95 악화 ≤0.3µm.
- ③ 기존 val 40에서도 결정3의 3조건(깊이·중간CD·롤아웃) 합격 유지(드리프트 데이터로
  재학습한 뒤 기존 조건 성능이 떨어지는 것 방지).
- α = 0.05 ÷ 재학습 루프의 최대 시도 횟수(ADR-0002 기준 4회 → **0.0125**, 본페로니 보정) —
  시도를 반복할수록 우연히 통과할 확률이 커지는 걸 막는다.
- 평가 레시피는 `golden_drift 10 + val 10`(20개) — **이건 이미 W6-04/05의
  `state.eval_ids()`가 쓰는 조합과 같다**[확인, `retrain/execute.py::DriftState.eval_ids`],
  그대로 재사용 가능.

ADR-0004가 "직전 대비 나빠도 CD/깊이/롤아웃이 기준 내면 막을 이유가 약하다"고 판단했던
근거를, 이 결정이 "통계적으로 유의하게 나빠지지 않았다는 걸 확인하자"는 쪽으로 뒤집는다 —
**ADR-0004 결정2의 ③ 다운그레이드를 부분적으로 되돌리는 결정**이라는 점을 명시한다.

### 재결정: 관문 B(개선 검정)·"정기 재학습" 분기는 이 ADR 범위에서 제외 [사용자 결정 2026-11-13]

문서는 관문 B(레시피별 표면 Dice 윌콕슨 개선 검정, p<α)를 "챔피언이 합격 상태(정기
재학습)"일 때 A+C와 함께 적용하라고 정의한다. 그런데 우리 C8/ADR-0002에는 드리프트
트리거 말고 "정기 재학습" 코드패스가 아예 없다[확인, `docs/project-design.md`·
`project-definition.md` 전체에 "정기" 개념 없음]. **이번 구현은 드리프트 트리거
경로(A+C)만 다룬다 — 관문 B는 통째로 구현하지 않는다.** "정기 재학습"을 새로 도입할지는
이 ADR의 범위 밖이며, 도입하려면 트리거 조건부터 별도 ADR이 필요하다.

**범위 축소의 실질적 효과**: 관문 C①도 윌콕슨 검정을 쓰므로, 이 ADR이 구현해도 통계
검정 인프라(`scipy.stats.wilcoxon`) 자체는 필요하다 — 관문 B를 빼도 "통계 검정 없음"이
되는 건 아니고, "표면 Dice 개선 검정(B)만 없음"이 된다.

## 결정 5: 드리프트 재학습 트리거 기준 변경

**기존**(`retrain/monitor.py::check_drift`): 드리프트 레시피 10개 평균 Chamfer가
`champion_golden_chamfer × 1.5` 초과 시 트리거.

**신규**: 드리프트 레시피 10개에 결정 3의 3조건(깊이·CD·롤아웃)을 적용해 챔피언의 충족
비율이 90%(9/10) 미만이면 트리거. 지표 자체가 Chamfer 비율에서 레시피 통과율로 바뀐다.

문서는 이 판정이 레시피 10개뿐이라 통계적 검정력이 낮다고 스스로 밝힌다(9/10 충족 시
95% 하한 0.61) — **트리거 신호로만 쓰고, 승격 판정은 결정 3·4의 20개 이상 기준으로
한다**[문서 §10 한계, 반영].

## 결정 6: `configs/pipeline/gate.yaml` 스키마 변경

```yaml
# 기존: max_chamfer, grid, max_dim_pct, max_regression, rollout_max_ratio, max_latency_s
# 신규:
max_chamfer: 0.3          # 참고값(차단 안 함, 결정1 Chamfer 용도 유지)
grid: 0.3                 # 유지 — 깊이 오차 하한(max(5%, grid)), 문서 값과 동일해 이름만 유지
max_dim_pct: 5.0           # 유지 — 깊이·CD 공용 퍼센트 기준(문서 "5%")
cd_floor: 0.6             # 신규 — CD 오차 하한만 grid(0.3)에서 분리(결정6 본문 이유)
rollout_max_ratio: 2.5    # 결정3 (기존 2.0에서 변경)
rollout_min_increase: 0.3 # 결정3 (증가량 하한, OR 조건) — 신규
recipe_pass_rate: 0.9     # 결정3 — 신규
alpha: 0.05               # 결정4 — 문서의 "정기 재학습 1회" 분기 전용 값이나, 그
                           # 분기 자체가 지금 우리 파이프라인에 없다(결정4 참고).
                           # 코드패스가 생기기 전까지는 미사용 상수로 남겨둔다.
alpha_retrain: 0.0125     # 결정4 (드리프트 루프, 본페로니 보정) — 실제로 쓰이는 값
max_latency_s: null       # 유지 — ⑤ 경고 전용, 이 ADR과 무관(변경 없음)
# 삭제: max_regression — ③ 다운그레이드가 결정4로 대체되어 더 이상 쓰이지 않음
```
`grid`/`max_dim_pct`/`max_latency_s`는 **삭제·개명 없이 유지**, `max_regression`만
삭제한다(결정4의 윌콕슨 검정이 그 역할을 대체) — 이전 버전의 "기존/신규가 겹치는 게
없다"는 표기는 부정확했다[2026-11-13 재확인, 정정].
깊이 쪽 하한(0.3µm)은 유지하되 CD 쪽을 `cd_floor`로 분리 — 문서 실측: 5%만 쓰면 val 40 중
27개 레시피가 0.6µm 미만 범위에서 판정이 격자 해상도 이하로 갈림[문서 §5].

`max_chamfer`는 **값만 바뀌는 게 아니라 산출 방법론 자체가 다르다**: 기존 0.582는
"첫 정상 모델의 val40 중앙값 Chamfer × 1.5"(모델 성능 기준, 체크리스트 W5-04), 신규
0.3은 "정답 격자 간격(grid_delta)"(시뮬레이션 해상도 기준, 문서 §5) — 더 이상 모델
실측값에 의존하지 않아 "첫 정상 모델이 바뀌면 기준도 바뀌는" 기존의 약한 재현성 문제가
없어진다.

구현 순서를 비용·위험도로 나눈다 — 한 번에 다 바꾸지 않는다(CLAUDE.md 작업규칙 1: 동시
진행 최대 2개).

- **1단계(저비용·저위험)**: 결정 1·2·2-1·6(지표 신설·재정의, 추론 속도 비 추가, 설정값
  갱신). 순수 함수 변경 + 상수 변경이라 영향 범위가 좁다.
- **2단계(고비용·고위험)**: 결정 3·4·5(게이트 집계 축 전환, 통계 검정 신설, 드리프트
  트리거 교체). `gate.py` 핵심 로직 재작성 + 기존 `test_gate.py`/W5-06·W5-08 부정 테스트
  기대값 재작성 + `GateResult` 스키마 변경이 레지스트리 카드·서빙(`inference.py`)·대시보드
  게이트 이력 화면(`history.js`)까지 전파되는지 확인 필요.

## 대안 (기각)

- **부분 채택(지표 재정의만 하고 게이트 집계 축은 유지)**: 결정 1·2·6만 받아들이고 결정
  3·4·5는 보류. 비용은 가장 작지만, 문서가 지적한 핵심 약점(평균 집계가 개별 레시피
  실패를 가림)을 그대로 남겨 "회귀 게이트"의 설계 목적과 어긋난다 — 1단계로 비용을 낮추되
  2단계도 같은 ADR 범위에 포함해 전부 채택하기로 함.
- **전체를 한 번에, 단계 구분 없이 반영**: 시간 여유가 있어도 `gate.py` 핵심 로직과 기존
  부정 테스트가 동시에 바뀌면 실패 원인을 구분하기 어려움 — 기각, 1·2단계로 분리.

## 해결된 항목 (2026-11-13 사용자 확인)

- **평가 방식 — 후처리 유지로 결정**: 지금 평가·게이트 파이프라인
  (`rollout_val_error_by_step(..., fix_mask=True, guard=True, loop_removal=True)`)이
  롤아웃 중 적용하는 마스크 고정·가드레일·루프 제거는 **그대로 유지한다**[사용자 결정
  2026-11-13]. 문서 §1 "후처리 없이 채점"은 "채점 단계에서 결과를 추가로 보정/필터링하지
  않는다"는 뜻으로 해석하고, 롤아웃 **예측 생성 과정** 자체에 포함된 이 세 보정은 "채점
  후처리"가 아니라고 본다 — 이 ADR의 전제(지표 재정의·게이트 집계 축 변경만으로 끝나는
  범위)는 그대로 유지된다. 평가 하네스 자체는 바꾸지 않는다.

- **val 40 반복 재사용 위험 — 이미 해결돼 있음**: 코드 확인 결과, 프로젝트에는 이미
  val과 분리된 `test` 분할(40개, `r0340`~`r0379`)이 있고 `docs/data_card.md` §3이
  "최종 평가"로 명시해 뒀다[확인]. 더 중요한 건 **`gate.py`·`monitor.py`·
  `retrain/execute.py`·`retrain/loop.py` 어디에도 `test` 분할을 읽는 코드가 없다**
  [확인, 2026-11-13 전수 grep] — `test`는 `scripts/run_model_comparison.py`(W6-12,
  모델 A/B 비교 1회)와 `eval.py --split test`(수동 호출) 두 곳에서만 쓰인다.
  즉 게이트·승격·재학습 루프는 구조적으로 `val`만 반복 사용하고 `test`는 건드리지
  않는 분리가 이미 돼 있어, 문서 §10이 말하는 "최종 성능은 별도 테스트셋으로 한 번만
  확인"을 이미 만족한다. **이 ADR의 구현(결정3·4·5)도 이 원칙을 유지한다 — 새 게이트
  로직·통계 검정 어디에도 `test` 분할을 연결하지 않는다.**
