# ADR-0007: 데이터 버전·백업 정책 — 외부 배포본 재업로드 기준

- 날짜: 2026-11-24
- 상태: **승인(사용자 결정 2026-11-24, W9-02 완료 처리)**
- 영향 파일: `docs/data_card.md` §4/§6(기준 인용 추가), `docs/project-checklist.md` W9-02.
  코드 변경 없음 — 정책 문서 ADR.
- **범위 제외**: 실제 재업로드 실행(GitHub Release/Hugging Face 쓰기 액션)은 이 ADR의
  범위가 아니다 — 매 사례마다 사용자가 직접 수행(아래 결정 4 참조).

## 배경

raw 데이터 생성 이후 두 번 버그가 발견됐다: W3-11(ETL 단계 SDF 경계 버그, raw 자체엔
영향 없음)과 W3-12(OOD 12건 중 5건이 물리적으로 불가능한 음수 에너지 — raw 데이터
자체의 버그). W3-12는 로컬 `data/raw/`를 재생성·백업했지만, 외부 배포본(GitHub Release
`data-v1-n400` 태그, Hugging Face `code5312/etch-ai-automation-data`)은 구버전 그대로
남았다.

W8-03에서 데이터 카드를 최종화하며 "외부 배포본을 재업로드할지"를 처음 공식적으로
물었다(AskUserQuestion). 1차 결정은 "직접 재업로드"였으나, 같은 날 사용자가 "굳이
외부에서는 안 해도 될 것 같아"로 **반전** — 재업로드하지 않음으로 최종 확정
(2026-11-14, `docs/data_card.md` §4, 증거: `reports/evidence/W8-03_readme_cards.md`).

두 결정 사이에 명시적 기준이 없었다 — 즉흥 판단이었다. 다음에 비슷한 데이터 버그가
나오면 같은 논의를 원점에서 다시 해야 하는 상태였다. 이 ADR은 "재업로드할지"를 매번
처음부터 논의하지 않도록, 사전에 합의된 1차 판단 기준을 만든다 — 최종 결정권은
여전히 사용자에게 있다(아래 결정 4).

## 결정

**1. 재업로드 검토 트리거** — 다음 중 하나 이상이면 "재업로드 검토 대상"으로
분류해 AskUserQuestion으로 제안한다. 해당 없으면 기본값은 "재업로드 제안하지 않음,
데이터 카드에 한계로만 기록":

- (a) `validate_data.py`(스냅샷 개수·NaN/Inf·점 수·깊이 비감소만 검사)가 잡지 못하는
  종류의 물리적 무결성 버그(예: 음수 에너지처럼 파라미터 범위 자체가 물리적으로
  불가능).
- (b) 영향받은 샘플이 특정 split(train/val/test/ood) 전체 또는 그 상당 비율에 걸침.
- (c) 버그가 게이트(G1~G8) PASS/BLOCK 판정 자체를 바꿀 수 있는 수준.

이 기준을 W3-11/W3-12에 소급 적용하면: W3-11은 raw 자체에 영향 없어 트리거
미해당(실제로도 재업로드 논의 없었음). W3-12는 (a)에 해당해 트리거 대상이었고,
실제로 AskUserQuestion까지 갔다 — 그런데 최종 결정은 "안 함"이었다. 즉 트리거는
"제안할지"를 결정할 뿐, 최종 결정은 항상 사용자 몫이라는 걸 이 사례 자체가 보여준다
[확인].

**2. 버전 관리** — 기존 외부 태그(`data-v1-n400`)는 불변 — 한 번 배포한 버전을
소급 수정(덮어쓰기)하지 않는다. 재업로드가 결정되면 새 버전(`data-v1.1-n400` 등,
변경 규모에 따라 마이너/메이저 결정)으로 추가 배포하고, 데이터 카드에 두 버전의
차이를 명시한다 — 이미 구버전을 내려받은 사용자의 데이터가 조용히 바뀌지 않게.

**3. 로컬 백업** — raw 데이터가 재생성될 때마다(버그 수정이든 확장이든) 덮어쓰기 전에
사용자 확인 하에 이전 버전을 로컬에 보존한다 — W3-12에서 실제로 한 패턴
("영향받은 ood 12건 재생성·로컬 백업 완료")을 일반 규칙으로 승격.

**4. 실행 주체** — GitHub Release/Hugging Face에 대한 실제 쓰기 액션은 Claude가 대신
실행하지 않는다(계정·권한 문제, CLAUDE.md 금지 목록 "사용자 확인 없이 ... 외부 서비스
가입 금지"와 같은 취지). Claude의 역할은 트리거 판단과 제안까지이고, 실제 업로드는
항상 사용자가 직접 수행한다.

## 비용·트레이드오프

기준을 미리 정해두면 사후 즉흥 판단(이번처럼 결정이 왔다갔다하는 것) 비용은 줄지만,
기준이 모든 미래 사례를 커버하지는 못한다 — "미해당"이어도 사용자가 재업로드를 원할
수 있고 "해당"이어도 반려할 수 있다. 이 기준은 1차 판단을 돕는 보조 장치일 뿐 강제
규칙이 아니다[제안, 실제 다음 사례에서 재검증 필요].

## 대안 (기각)

- **매 버그마다 원점 재논의**: 이미 한 번 비용을 치름(W8-03의 결정 반전) — 기각.
- **"항상 재업로드" 규칙**: 사소한 버그마다 외부 배포본 버전을 늘리면 "어떤 버전이
  최신·신뢰할 수 있는지" 사용자 쪽 혼란이 커짐 — 기각.
- **"절대 재업로드 안 함" 규칙**: 향후 더 심각한 무결성 버그(게이트 판정에 영향 주는
  수준)가 나와도 외부에 방치되는 리스크를 감수해야 함 — 기각.
