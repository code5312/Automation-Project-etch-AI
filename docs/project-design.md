# 프로젝트 설계서: 식각 공정 AI 대리 모델 개발 자동화 파이프라인

- 버전: v0.1 (초안) / 작성일: 2026-10-18
- 연결 문서: `project-definition.md`(프로젝트 정의서)
- 태그 규칙: **[근거]** NVIDIA 문서·논문에서 확인 / **[제안]** 팀 설계값(측정 후 조정) / **[확인필요]** 1주차에 검증

---

## 0. 쉬운 말로 먼저

> 느리지만 정확한 시뮬레이터(선생님)가 푼 문제집으로 빠른 AI(학생)를 가르친다. 학생이 **표준 시험(회귀 게이트)을 통과해야만** API로 내보내고, 성적이 떨어지면 **자동으로 다시 가르친다.** 우리가 만드는 것은 AI 학생 자체가 아니라, 이 "문제집 제작 → 교육 → 시험 → 배포 → 재교육"이 자동으로 도는 시스템이다.
> 

## 1. 목표와 비목표

### 1.1 목표

1. 설정 파일 한 번으로 **데이터 생성 → 변환 → 학습 → 평가 → 게이트 → 등록 → 서빙**이 끝까지 자동 실행된다.
2. 모델 2종(MeshGraphNet, FNO)을 같은 틀에서 학습·비교하고 비교표를 자동 생성한다.
3. 게이트가 부실한 모델을 실제로 차단한다(시연 가능).
4. 드리프트(시뮬레이터 계수 변경) 발생 시 재학습이 사람 개입 없이 1회 완주한다.
5. 같은 입력·같은 설정이면 같은 결과가 나온다(재현성).

### 1.2 비목표 (이번 범위 밖)

- 모델 성능 극대화, 새 아키텍처 연구
- 경제성 분석 (측정값 나열만)
- 3D, 반응기 스케일 연동, 원자 수준 모델
- 실제 팹 데이터·실제 장비 제어
- 실시간 센서 수집(Kafka/MQTT), 3D 디지털 트윈

## 2. 전체 구조

```
┌─ C1 시뮬레이션 러너 (ViennaPS)
│     설정(범위·시드) ─▶ 레시피 샘플링 ─▶ 시뮬레이션 일괄 실행 ─▶ raw/ (불변)
│
├─ C2 ETL (Curator 파이프라인)[Extract(추출), Transform(변환), Load(적재)의 약자]
│     raw/ ─▶ 그래프 변환(모델 A용) / SDF 격자 변환(모델 B용) ─▶ processed/ (+ 해시 버전)
│
├─ C3 학습 (PhysicsNeMo)
│     processed/ ─▶ 모델 A 학습, 모델 B 학습 ─▶ 체크포인트 + 지표 JSON
│
├─ C4 평가
│     체크포인트 ─▶ 지표 계산(Chamfer, IoU, CD, 깊이, 테이퍼, 범위 밖 오차) ─▶ 리포트
│
├─ C5 회귀 게이트
│     골든 레시피 10종 평가 + 이전 모델 대비 비교 ─▶ PASS / BLOCK
│
├─ C6 레지스트리
│     PASS 모델만 등록(버전, 데이터 해시, 설정, 지표)
│
├─ C7 서빙 (API)
│     레지스트리의 현재 모델 로드 ─▶ /predict ─▶ 프로파일 + 지표 + in_range 플래그
│
├─ C8 재학습 트리거
│     신규 데이터/드리프트 감지 ─▶ C2~C6 재실행
│
└─ C9 대시보드
      예측 vs 정답 오버레이, 모델 비교표, 게이트 이력
```

데이터 흐름은 한 방향(C1→C7)이고, C8이 C2 이후를 다시 호출하는 **되돌이 한 줄**만 있다. 단계 사이는 **파일과 설정 파일로만 연결**해서(함수 직접 호출 최소화) 각 단계를 따로 개발·테스트할 수 있게 한다. [제안]

### C1. 시뮬레이션 러너

| 항목 | 내용 |
| --- | --- |
| 책임 | 설정(파라미터 범위, 샘플 수, 시드)으로 레시피를 만들고 ViennaPS를 일괄 실행 |
| 입력 | `configs/sim/*.yaml` |
| 출력 | `data/raw/<run_id>/{params.json, snapshots/*, meta.json}` (불변) |
| 기술 | ViennaPS Python 바인딩(`import viennaps as vps`), 레시피 샘플링은 Sobol/LHS [근거: ViennaPS 사용법 / 제안: 샘플링] |
| 핵심 규칙 | 시뮬레이터 내부는 수정하지 않고 `run_sim(params, out_dir)` 함수로 **감싼다.** 시드·레이 수·ViennaPS 버전을 `meta.json`에 기록. 실패 건은 재시도 후 로그에 남기고 이어하기 지원 |
| 병렬·스케줄링 | **Kubernetes Indexed Job**. 레시피를 N개 샤드로 나누고 파드 1개가 샤드 1개를 처리한다(파드에 자동 주입되는 `JOB_COMPLETION_INDEX`로 샤드 결정). 파드 단위 재시도, 끝난 건은 건너뛰어 이어하기. 로컬 개발·시연은 `kind`/`minikube`/`k3d` 중 하나 [제안]. `src/sim_batch.py`의 샤드·이어하기 로직은 로컬 실행으로 확인, **클러스터 실행은 미확인** |
| 저장소 | 파드들이 같은 `data/raw`에 쓰므로 공유 볼륨(PVC)이 필요. 노드가 여러 대이면 ReadWriteMany 가능한 스토리지 또는 객체 스토리지 업로드가 필요 [제안] |
| 이미지 | `docker/Dockerfile.sim` (`ViennaPS==4.5.0` + `ViennaLS==5.8.5` 고정). 이미지 빌드는 미확인 |
| 대체 경로 | 클러스터를 못 구하면 같은 `sim_batch.py`를 `xargs -P`로 실행 (코드 변경 없음) |
| 관련 요구사항 | FR-01, FR-02, FR-03 |

### C2. ETL (데이터 변환)

| 항목 | 내용 |
| --- | --- |
| 책임 | raw 스냅샷 → 모델 A용 그래프, 모델 B용 SDF 격자 |
| 기술 | 순수 파이썬 `etl.py`: `.vtp` 읽기(pyvista) → 그래프/거리장 변환 → 저장. 샌드박스에서 2건으로 동작 확인 [확인] |

| 관련 요구사항 | FR-04, FR-05 |

### C5. 회귀 게이트

## 4. 데이터 설계

### 4.1 디렉터리 규칙

```
data/
  raw/<run_id>/                # 시뮬레이션 원본, 불변
    params.json                # Θ 7개 값
    meta.json                  # 시드, 레이 수, ViennaPS 버전, 소요 시간
    snapshots/step_00.*, ...   # 시간 t_k 별 표면 (K≈20~30장)
  processed/<dataset_hash>/
    graphs/…                   # 모델 A
    sdf/…                      # 모델 B
    splits.json                # train/val/test/ood 레시피 ID 목록
    stats.json                 # 정규화 통계 (train 기준)
golden/                        # 골든 레시피 10종 + 고정 정답 (재생성 금지)
runs/<run_id>/                 # 학습 산출물
reports/<run_id>/              # 평가·게이트 결과
registry/<model_id>/           # 배포 모델 + 모델 카드
```

### 4.2 입력 파라미터 Θ (7차원) [제안, 키 이름은 ViennaPS 예제 설정 기준 확인필요]

이온 플럭스, 식각제(F) 플럭스, 산소(O) 플럭스, 평균 이온 에너지, 이온 각도 지수, 마스크 폭, 마스크 높이.
범위는 ViennaPS SF6/O2 예제 기본값 근방(대략 ×0.3~×3 또는 ×0.5~×2)에서 시작하고, 이 범위가 모델의 **유효 범위**가 된다.

### 4.3 규모 (시작점) [제안]

train 300 / val 40 / test 40 / OOD 20 레시피. NVIDIA 와류 예제(1000/100/100 샘플)를 참고 기준으로 삼았고 [근거], 시뮬레이션 1건 시간을 측정한 뒤 확정한다. 부족한 영역은 불확실성 기반으로 추가 생성(능동 학습)한다.

### 4.4 버전 관리

- 데이터: 내용 해시를 `dataset_hash`로 사용, DVC 등으로 추적 [제안]
- 코드: git SHA를 모든 `runs/` 결과에 기록
- 모델 ↔ 데이터 ↔ 설정은 **모델 카드 한 장**으로 역추적 가능해야 한다.

## 7. API 설계 (C7) [제안]

| 엔드포인트 | 용도 |
| --- | --- |
| `POST /predict` | 레시피 배치 → 프로파일·지표 |
| `GET /model` | 현재 배포 모델의 버전, 데이터 해시, 유효 범위, 게이트 결과 |
| `GET /health` | 상태 확인 |

`POST /predict` 요청/응답 개요

```json
// request
{ "recipes": [ { "ion_flux": 1.0, "etchant_flux": 1.0, "oxygen_flux": 1.0,
                 "ion_mean_energy": 1.0, "ion_exponent": 1.0,
                 "mask_width": "mid", "mask_height": "low" } ],
  "times": [0.25, 0.5, 1.0] }
// response
{ "model_version": "m-0007",
  "results": [ { "profiles": [ {"t": 0.25, "points": [[x,y], ...]} ],
                 "cd": 0.0, "depth": 0.0, "taper_deg": 0.0,
                 "in_range": true } ] }
```

(수치는 형태 예시이며 실제 단위는 ViennaPS 설정 확인 후 확정)

**입력 검증 규칙**: 필수 키 누락·타입 오류는 422, 한 요청의 배치 크기 상한, 수치 범위 상·하한(비정상 값 거부), 요청 크기 제한. 유효 범위 밖은 거부하지 않고 `in_range=false`로 **경고만** 한다(사용자가 의도적으로 탐색할 수 있게). [제안]

| 워크플로우 | 트리거 | 하는 일 | GPU |
| --- | --- | --- | --- |
| `pr-check` | PR 생성/수정 | 린트, 단위 테스트, 설정 스키마 검증, 금지 표현 검사 | 불필요 |

| `train-eval` | 수동 호출 또는 설정 변경 | 학습 → 평가 → 게이트 → 등록(PASS 시) | 필요(셀프호스트 러너 또는 수동 실행) |
| `retrain-demo` | 수동 호출(드리프트 데이터 지정) | C8 재학습 시나리오 전체 | 필요 |
| `nightly`(선택) | 일 1회 | 골든 재평가로 환경 변경 감지 | 선택 |
- GPU 러너가 없으면 `train-eval`은 팀 서버에서 수동 실행하고, 결과 JSON을 CI가 검증하는 구성으로 대체한다.
- PASS 판정이 아닌 모델은 `registry/`에 쓰이지 않는다(쓰기 권한은 게이트 단계만 가진다).

## 9. 테스트 전략

| 층 | 대상 | 방법 |
| --- | --- | --- |
| 단위 | 샘플러, 그래프/SDF 변환, 지표 계산, Chamfer 구현 | 해석적으로 답을 아는 입력(직선, 원 등)으로 검증 |
| 물리 타당성 | 시뮬레이션 출력 | 보존·단조성 같은 간단한 성질(식각 깊이가 시간에 따라 감소하지 않음 등), 문헌과의 정성 비교 |
| 재현성 | 파이프라인 | 같은 시드·설정으로 두 번 실행해 지표 허용 오차 내 일치. 비결정 요소(GPU 연산, 몬테카를로) 목록화 |
| 게이트 | C5 | §3 C5의 자체 테스트(노이즈/1에폭/시뮬레이터 버전 변경 모델, 해시·골든 변조)가 모두 BLOCK |
| 통합 | 전 단계 | 샘플 수를 10배 줄인 **스모크 설정**으로 처음부터 끝까지 완주(CI에서 수 분 내) |
| 서빙 | API | 정상/경계/비정상 입력, OOD 플래그, CPU 추론 지연 측정 |

LLM이 작성한 코드와 설명도 위 검증을 거친다. **물리적 타당성은 LLM이 아닌 테스트와 문헌으로 확인**한다.

## 10. 보안·운영 고려 [제안]

- 서빙 입력 검증과 배치·요청 크기 제한, 요청 빈도 제한
- 모델 아티팩트 SHA-256 검증(변조·손상 감지), 레지스트리 쓰기 권한 분리
- 의존성 버전 고정(lock 파일), 컨테이너 이미지 태그 고정 — 특히 ViennaPS(`ViennaPS==4.5.0`, `ViennaLS==5.8.5` 조합에서만 import 확인)
- 비밀값(토큰 등)은 저장소에 두지 않고 CI 비밀 저장소 사용
- 로그에 모델 버전·입력 해시를 남겨 추적 가능하게 한다.

## 14. 1주차 스파이크 (착수 전 확인)

체크리스트 W1-S0~S6과 1:1로 대응한다.

- S0: CI에서 `ViennaPS`·PyG·`torch_scatter` 설치 성공 확인(실패 시 캐시·사전 빌드 이미지로 대응)
- S1: ViennaPS SF6/O2 예제로 레시피 20개 실행: 소요 시간 분포(최소/평균/최대, 코어 수), 깊이 분포, 파라미터 키·단위 확정 → `depth_max`·N 결정
- S2: 동일 레시피·시드로 2회 실행 → 스냅샷 일치 여부(불일치 시 비결정 요소·허용오차 정의)
- S3: PhysicsNeMo 와류(vortex shedding) 예제로 백엔드·그래프 입력 규약 확인 후, 식각 레시피 3~5개로 MeshGraphNet 소규모 과적합·다단계 롤아웃 사전시험(발산 여부 확인)
- S4: Docker 설치 확인 → `Dockerfile.sim` 빌드 → `kind` 클러스터 → `sim-job-local.yaml` 파드 4개 `Completed` → 파드 1개 삭제 후 재시도·이어하기 확인(실패 시 `xargs -P` 경로 확정)
- S5: `.vtp` 셀 데이터에서 `MaterialIds` 0/10의 재료 매핑 확정 → `configs/etl/materials.yaml`
- S6: FNO 모듈 경로·시그니처를 설치본 소스에서 확인, 128×256 입력 forward/backward 1회, CPU 1에폭 시간 측정
- 마지막: 결과로 본 문서의 [확인필요]를 모두 갱신

비고
- `.vtp`→그래프/거리장 변환 최소 예제는 샌드박스에서 이미 동작 확인됨 [확인, 정의서 §10] — 위 스파이크 범위 아님.
- MeshGraphNet 1에폭 학습 시간·메모리(CPU, 노드 300~400개, 약 40~180ms/스텝)는 샌드박스에서 이미 측정됨 [확인, 정의서 §10] — 위 스파이크 범위 아님.
- 능동 학습(선택 범위, 정의서 §5.2)은 증거 ①②를 확보하기 전에는 착수하지 않는다 — 1주차 스파이크에서 제외.

## 16. 용어 (쉬운 설명)

- **식각**: 반도체 표면을 깎아 홈을 파는 공정 / **트렌치**: 그렇게 생긴 좁고 긴 홈 / **프로파일**: 홈의 단면 모양
- **ViennaPS**: 식각 결과를 계산해 주는 공개 시뮬레이터(선생님) / **대리 모델**: 그 결과를 배워서 빠르게 맞히는 AI(학생)
- **SDF**: 바둑판 칸마다 "깎인 면까지 거리"를 적은 표 / **그래프**: 윤곽선 위 점을 선으로 연결한 구조
- **Chamfer 거리**: 예측 윤곽선과 정답 윤곽선이 평균 얼마나 떨어져 있는지 / **CD**: 홈의 폭
- **회귀 게이트**: 표준 문제 10개 시험에 통과해야 배포하는 장치 / **골든 세트**: 그 표준 문제와 고정 정답
- **OOD**: 학습한 적 없는 범위의 입력 / **유효 범위**: 모델이 믿을 만한 입력 범위
- **레지스트리**: 합격한 모델만 보관하는 창고
- **드리프트**: 장비·조건이 변해 기존 모델이 틀리기 시작하는 현상
