# W8-02: 한계 분석

CLAUDE.md 4항("실행해 보지 않은 것은 사실로 쓰지 않는다")에 따라, 이 문서는 실제로
확인된 사실([확인])과 아직 검증되지 않은 채 남은 항목([미확인])을 구분해서 적는다.
숫자는 모두 기존 증거 파일에서 인용했다(이 문서에서 새로 계산한 값 없음).

## 1. 2D 한정 [확인, 처음부터 명시된 범위]

- 시나리오 자체가 "2D 트렌치 식각 1종(SF6/O2, Si+마스크)"로 정의돼 있고, 3D/디지털
  트윈/KMC·MD 멀티스케일은 명시적으로 제외 범위다(`docs/project-definition.md` §5.1,
  §5.3). 출력 포맷 자체도 2D 선분 메시(.vtp)다(같은 문서 §7.2). 대시보드도 2D만
  표시한다(`docs/project-design.md` §9 C9, "2D만 [제안]").
- 이건 "시간이 없어서 못 한" 미구현이 아니라 **처음부터 정한 범위 경계**다 — ADR이나
  별도 타당성 분석 없이 정의서 1건으로 고정됐고, 프로젝트 기간 내 재검토된 적 없다.
  3D로 확장했을 때 어떤 물리 현상(측벽 프로파일의 깊이방향 비균일성 등)을 놓치는지는
  이 프로젝트의 범위 밖이라 분석하지 않았다[미확인, 범위 밖].

## 2. 가상 데이터 [확인]

- 모든 데이터는 ViennaPS(오픈소스 2D 공정 시뮬레이터)로 생성한 **합성 데이터**다.
  실제 양산 설비 계측값이 아니며, 특정 업체의 실제 모델·수치를 재현하지 않는다
  (`docs/data_card.md` 10~11행, `docs/project-definition.md` §2, §6).
  "실제 fab 데이터", "SK하이닉스 모델 재현" 같은 표현은 금지 표현 목록에 올라 있고
  (§6), W7-06/08에서 코드·문서 전체를 재검사해 위반 0건을 확인했다.
- **ViennaPS 시뮬레이터 자체의 물리적 정확도(실제 식각 공정과 얼마나 맞는지)는 이
  프로젝트의 검증 대상이 아니다** — `docs/data_card.md` 90행에 명시돼 있고, 실제 계측값과
  대조·검증한 적이 없다(같은 문서 75행). 즉 이 파이프라인이 "정확하다"고 말할 수 있는
  범위는 **ViennaPS가 내놓은 답을 얼마나 잘 재현하는가**까지이며, ViennaPS 자체가
  실제 공정과 얼마나 가까운지는 전혀 다른, 검증되지 않은 질문이다[미확인, 범위 밖 —
  이 경계를 넘는 주장은 금지 표현 규칙으로도 막혀 있음].

## 3. 유효 범위 [확인]

입력 Θ(7차원)의 "유효 범위"는 두 가지 서로 다른 메커니즘으로 다뤄진다 — 섞어서
설명하면 오해를 부르므로 구분한다.

1. **물리적으로 말이 안 되는 값은 거부(422)**: `src/etchpipe/serve/app.py`의
   `Recipe` 모델이 각 필드에 상식적 상·하한을 건다(예: `ion_flux: gt=0, le=300.0`).
   이건 학습 범위와 무관하게 "0 이하/터무니없이 큰 값"만 막는다(코드 주석,
   `app.py:70` 부근).
2. **학습 범위 밖은 거부하지 않고 경고만(`in_range=false`)**: 레지스트리 카드의
   `valid_range`(`registry.py::compute_valid_range`)를 기준으로
   `inference.py::is_in_range()`가 판정한다. 범위를 벗어나도 추론은 수행하고
   플래그만 켠다 — 이건 사용자가 의도적으로 탐색할 수 있게 하자는 결정이고,
   **DOC-01로 이미 기록·확인됨**(`docs/project-checklist.md:425`,
   `reports/evidence/W6-08_predict_real_model.md`).
3. 정의서 §7.1의 7차원 범위 표(`ion_flux: 3~30` 등)는 `[제안]` 태그가 붙어 있다 —
   실제로 레지스트리에 기록되는 `valid_range`는 학습 데이터(train 300개)의 실제
   분포에서 계산되므로, 이 표의 숫자와 정확히 같다고 보장되지 않는다[미확인,
   표 대 실제 레지스트리 값 1:1 대조는 하지 않았음].
4. **범위가 실제로 중요하다는 증거**: OOD(학습 범위 밖) 20개 레시피 평가에서 Chamfer가
   val 대비 **5.8배**, 깊이오차가 **12.4배**로 뛴다(모델 A,
   `reports/eval/mgn_tuned_ood20/metrics.json`, `reports/evidence/W5-03_ood_eval.md` —
   W8-01 §4와 동일 인용). `in_range=false` 경고는 장식이 아니라 실측으로 뒷받침된
   경고다.

## 4. 보잉·언더컷 구간 오차 [미확인 — 구조적 한계, 숨기지 않고 명시]

이 항목이 한계 분석에서 가장 중요하다: **보잉·언더컷 구간에서 모델이 얼마나 틀리는지,
실측 수치는 어디에도 없다.**

- `eval/metrics.py::bowing()` 함수는 구현·단위테스트(합성 마스크로만 — 직사각형
  트렌치는 0, 부푼 트렌치는 양수)됐지만, **함수 자신의 docstring이 "호출부 없음 확인,
  2026-11-14 — 영향 없음"이라고 적어 놓았다** — 실제 모델 롤아웃 결과에 대해 단 한
  번도 호출된 적이 없다. 보잉은 게이트 판정 기준(관문 A/C)에도 포함돼 있지 않다 —
  참고 지표로 설계됐을 뿐 집계되지 않았다(`docs/adr/0005-recipe-pass-rate-gate-and-stat-tests.md`
  결정2).
- **언더컷 전용 지표 함수는 저장소에 존재하지 않는다.** 대신 언더컷은 롤아웃 코드의
  **단순화 가정**으로 처리된다: `train/rollout.py`가 마스크를 t=0 시점에 한 번만
  만들고 모든 스텝에서 그대로 재사용한다("언더컷 제외"라고 코드에 명시). 즉 실제
  데이터에 언더컷이 나타나도 모델 구조상 표현할 수 없다.
- 이 한계는 새로 발견한 게 아니라 **프로젝트가 이미 4주차에 스스로 적어 둔 미확인
  항목**이다: `reports/evidence/W4-05_rollout_v1.md`(52~54행)가 "법선 부호 연속성
  가정이... 보잉·언더컷처럼 곡률이 큰 구간에서도 유지되는지는 실제 모델 롤아웃
  결과로만 확인 가능 — [미확인]"이라고 못 박아 뒀고, 8주차 끝까지 이 검증은
  이뤄지지 않았다.
- 긍정적인 부분: 보잉·언더컷 같은 비단조(非單調) 프로파일 자체는 **데이터 표현
  단계(SDF/ETL)에서는 정확히 처리된다** — 짝수-홀수 교차 판정으로 검증됨
  (`docs/adr/0003-signed-sdf-convention.md`, `tests/unit/test_etl.py`, 14 passed,
  `reports/evidence/W3-03_signed_sdf.md`). 즉 "데이터를 못 담는다"가 아니라
  "모델이 그 구간에서 얼마나 정확한지 측정한 적이 없다"는 것이 정확한 한계다.
- 결론: 골든10/val/test 중 실제로 보잉·언더컷이 뚜렷한 레시피가 몇 개나 있는지,
  그 레시피들만 따로 뗐을 때 오차가 다른 레시피보다 큰지 작은지 — **이 전부가
  미확인이다.** 측정하지 않은 것을 "괜찮다"고도, "나쁘다"고도 쓰지 않는다.

## 5. 미확인 항목 처리 결과

프로젝트 전체에서 남아 있는 미확인 항목을 모아, 각각 이번에 **명확화(처리)**했는지
아니면 **여전히 열려 있는지** 구분한다.

| 항목 | 상태 | 비고 |
|---|---|---|
| 추론 속도 비(`speed_ratio`) | 명확화 | 구현·단위테스트는 있으나 실측 보고 없음 — W7-08/W8-01에서 "구현됨, 미보고"로 확정 기재. 추가 실측은 향후 과제. |
| 모델 단독 forward 지연 | 명확화 | `measure_latency()` 호출부 0건 확인(W8-01) — end-to-end 19~20초만 유일한 실측치로 남김. |
| `max_latency_s` 게이트 임계치 | 열려 있음 | 미실측이라 설정하지 않은 상태 그대로 둔다(`configs/pipeline/gate.yaml`). |
| FNO(모델 B) OOD 20개 평가 | 열려 있음 | 저장소 전체에 평가 기록 없음(W8-01에서 확인) — 향후 과제로 명시. |
| 보잉·언더컷 구간 오차 | **열려 있음(핵심)** | 위 §4. `bowing()` 미호출, undercut 미지표화, W4-05의 자체 미확인이 그대로 유지됨. |
| 두 모델 학습 GPU 기종 미기록 | 열려 있음(낮은 우선순위) | 결과 재현성엔 영향 없음(코드·시드·데이터해시는 기록됨), 기종만 미기록. |
| 모델 A 평가 JSON `git_sha` 필드 손상 | 열려 있음 | 인코딩 문제로 보이나 이번 범위(문서 작업)에서 코드 수정은 하지 않음 — 버그로 별도 기록 필요. |
| 모델 A test-40 Chamfer 측정 파이프라인 불일치(0.378 vs 0.408) | 명확화 | 오류가 아니라 서로 다른 정의(W8-01 §0) — 혼용하지 않도록 표를 분리해 해결. |
| OOD +100건 확장 보류(`project-checklist.md:133`) | 열려 있음 | split 비율 변경이 필요해 DOC- 항목으로 여전히 사용자 확인 대기 중(수 주째 미결). |
| ViennaPS GPL-3.0 배포 영향 법적 검토 | 열려 있음(의도적) | §11의 격리 전략은 팀 결정(`[제안]`)이며 법률 자문으로 확정된 사실이 아님 — 포트폴리오/제출용 프로젝트 범위에서는 격리 조치 자체를 완화책으로 유지하고, 정식 법적 결론은 내리지 않는다. |
| ViennaPS 자체의 물리 정확도(실제 공정 대비) | 열려 있음(영구적, 범위 밖) | §2 참고 — 처음부터 검증 대상이 아니라고 선언된 항목. |

**요약**: 10개 항목 중 3개(추론 속도 비 상태, 단독 지연 상태, Chamfer 정의 불일치)는
이번 주차에서 "무엇이 맞는지" 명확화했고, 나머지 7개는 실제로 미해결 상태로 남아
있다 — 그중 보잉·언더컷 구간 오차가 가장 중요한 구조적 공백이다(§4). 미확인을
확인됨으로 둔갑시키지 않고 그대로 남긴다.
